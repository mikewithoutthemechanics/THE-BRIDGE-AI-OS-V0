# BridgeAI Environment Variable Audit — 2026-04-19

Classifies ~150 `process.env.*` references across BridgeAI workspaces by secrecy tier. Use for rotation prioritization.

**Scope:** JS files across `C:/aoe-unified-final`, `E:/BridgeAI/**`, `c:/aoe-unified-final-main` (scratch).
**Sibling Python layer:** `E:/BridgeAI/BridgeLiveWall/backend/app/**` — KeyForge consumes `BRIDGE_SIWE_JWT_SECRET`, `BRIDGE_INTERNAL_SECRET`, `JWT_SECRET`.

---

## Classification heuristic

A var that appears in [gateway.js](../../aoe-unified-final/gateway.js), [auth.js](../../aoe-unified-final/auth.js), or [brain.js](../../aoe-unified-final/brain.js) is touched on every request — leak = active compromise, not theoretical. A var appearing only in `hardhat.config.js` or a one-off script runs at build/deploy — leak-surface but not live-traffic-surface.

**Rotation blast radius** = count of files referencing the var. Each site must receive the new value.

### Consolidation candidates

The top two vars (`JWT_SECRET` at 25 files, `BRIDGE_INTERNAL_SECRET` at 16) are the most expensive to rotate because each consumer is a separate import that must be PM2-restarted. Wrapping both behind a small getter module (e.g., `lib/auth-secrets.js` with lazy `process.env.*` reads) would:

- Cut blast radius from 25/16 files to 1 each.
- Add a single point for rotation telemetry (log every first-read per process).
- Make future `KeyForge` migration trivial — replace the getter, not 25 call sites.

### Test-file exposure

Three nuclear vars are referenced from `tests/` — `JWT_SECRET` and `JWT_REFRESH_SECRET` (auth.test.js, super-admin-routing.test.js) and `BRIDGE_SIWE_JWT_SECRET` (agent-crypto-wallet.test.js). These must read from a CI-only `.env.test` (never the prod secrets) — verify [scripts/apply-p0-p1-batch.sh](../scripts/apply-p0-p1-batch.sh) doesn't carry prod values into test runs.

### Classifier evolution

Two real-data scans revealed three missed patterns. Current `classify()` in [scripts/env-usage-audit.sh](../scripts/env-usage-audit.sh) catches:

- **t0 additions:** `*_SESSION_SECRET`, `*_INTERNAL_SECRET`
- **t1 additions:** `*_SERVICE_KEY` (Supabase service role), `*_SHARED_SECRET` (advisor bearer tokens), `*_BOT_TOKEN`, `*_PRIVATE_TOKEN`, `*_DB_URL`, `*_SERVICE_ROLE`

If a new prefix appears in the codebase and lands in t3 incorrectly, patch `classify()` once and every future audit catches it.
